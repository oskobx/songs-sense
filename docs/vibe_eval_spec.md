# Phase 3b Spec: Vibe Search Evaluation

Builds a measurable benchmark for Vibe Search quality: a 100-query eval set generated by LLM and curated by the user, an LLM-as-judge for relevance grading, a 30-pair human-graded calibration set validating the judge, and a harness computing recall@k, MRR, and NDCG.

Designed to minimise manual labour. Total human time: ~1.5 hours, nearly all of it calibration grading.

## Goal

Produce a reproducible baseline number for Vibe Search. Every future change (reranker, fine-tuned embeddings, chunk-size tuning) gets measured against it.

Output artifacts:
- `data/eval/vibe_queries.json` — 100 queries
- `data/eval/calibration.json` — 30 human-graded (query, passage) pairs
- `data/eval/judge_cache.json` — cached LLM judgments
- `data/eval/results_<timestamp>.json` — per-run metric output

## Part 1: Eval set construction

### Structure

```json
{
  "queries": [
    {
      "id": "vibe_001",
      "query": "feeling lost in a city at night",
      "language": "en"
    }
  ]
}
```

No labeled songs. The judge grades everything at eval time. This is the main labour saving versus a labeled-ground-truth design, and it works only because the judge is calibrated.

### Language distribution

Corpus is 79% English, 8.7% Spanish, 5.6% Polish, 4% German. The eval set deliberately over-weights non-English, because the language-boost mechanism is recent and needs coverage:

| Language | Queries |
|---|---|
| English | 70 |
| Polish | 15 |
| German | 10 |
| Spanish | 5 |

Non-English queries must be written natively in that language, not translated word-for-word from English.

### Generation

`src/eval/generate_vibe_queries.py` prompts the LLM for queries across a spread of categories, then writes them to JSON for user review.

Categories to cover (roughly equal share):
- Emotional states — "the moment you realize it's over"
- Situations — "driving home alone after a long night"
- Abstract vibes — "nostalgic but not sad"
- Sensory or visual — "summer heat and cheap sunglasses"
- Relational — "loving someone who doesn't know yet"

Generation prompt shape:

```
Generate {n} "vibe search" queries for a lyrics search engine, in {language}.

A vibe query describes a feeling, mood, or situation someone wants songs about.
It is NOT a song title, artist name, or lyric quote.

Requirements:
- 4-12 words each
- Natural phrasing, the way a person would actually type
- Category: {category}
- Varied - do not produce near-synonyms of each other
- Written natively in {language}, not translated from English

Return one query per line, no numbering, no commentary.
```

**Critical anti-pattern:** do not generate queries from songs (pick a song, describe it, use as query). That guarantees a perfect match exists and inflates every metric. The generator must never see corpus content.

### User curation (~30 min)

A CLI shows each generated query; user presses `k` to keep or `d` to delete. Over-generate (~140) so ~100 survive.

Delete anything that is: a near-duplicate of an earlier query, a song title in disguise, too vague to have any answer ("music"), or too specific to be a vibe ("songs mentioning Tuesday").

## Part 2: LLM-as-judge

### Model

**GPT OSS 120B via Groq** (`openai/gpt-oss-120b`). Free tier, ~30 RPM.

Note: `llama-3.3-70b-versatile` is decommissioned 16 August 2026 - do not use it.

### Judge prompt

```
You are grading whether a song passage matches a "vibe search" query.

Query: {query}
Song: {artist} - {title}
Passage:
{passage_text}

Grade the match on this scale:
3 = excellent, this passage captures exactly the vibe described
2 = good, clearly relevant to the vibe
1 = marginal, tangentially related
0 = not relevant

Judge the passage's emotional and thematic content, not word overlap.
A passage in a different language than the query can still be an excellent match.

Respond with ONLY a single digit: 0, 1, 2, or 3.
```

Parse as integer. Retry once on unparseable output; default to 0 after that and log it.

### Volume and caching

100 queries x 10 results = 1,000 judgments per run. At 30 RPM, ~35 minutes uncached.

Cache keyed on `(query_id, passage_id)` in `data/eval/judge_cache.json`. Re-running against unchanged retrieval should make near-zero LLM calls. This matters - you will run the eval many times.

## Part 3: Calibration

Without this, there is no evidence the judge is trustworthy, and the absolute numbers mean nothing.

### Sampling

30 (query, passage) pairs sampled to span the grade range - roughly 10 from ranks 1-3, 10 from ranks 4-10, 10 from ranks 15-30. Sampling only top hits would produce a calibration set with almost no 0s and 1s, and the kappa would be meaningless.

Include non-English pairs proportional to the query mix.

### Grading interface

`src/eval/grade_calibration.py` - a CLI that shows one pair at a time:

```
[7/30]  Query: "driving home alone after a long night"
        Song: The Weeknd - Blinding Lights [en]

        The city's cold and empty (oh)
        No one's around to judge me (oh)
        …

        3 = excellent  2 = good  1 = marginal  0 = not relevant
        > _
```

Single keypress, auto-advance, `u` to undo the previous grade, progress saved after each entry so it survives interruption. Target ~90 seconds per pair, ~45 minutes total.

The user grades before ever seeing the judge's opinion on these pairs - no anchoring.

### Agreement metrics

`src/eval/calibrate.py` runs the judge on the same 30 pairs and reports:

- **Cohen's quadratic-weighted kappa** - primary. Grades are ordinal, so a 3-vs-2 disagreement should cost less than 3-vs-0.
- **Spearman correlation**
- **Exact-match rate** and **within-1 rate**
- 4x4 confusion matrix

### Interpretation

| Weighted kappa | Reading |
|---|---|
| > 0.75 | Strong. Trust the judge. |
| 0.60 - 0.75 | Acceptable. Report kappa alongside metrics. |
| 0.40 - 0.60 | Weak. Add few-shot examples to the prompt, re-measure. |
| < 0.40 | Unusable. Do not report absolute numbers. |

If below 0.60: pull 3-4 clear examples from the calibration set into the judge prompt as few-shot demonstrations, then re-run calibration. The calibration set is fixed, so iterations are free and fast.

**Report the kappa in the blog post.** "MRR = 0.71" is a much weaker claim than "MRR = 0.71, with an LLM judge validated at kappa = 0.78 against 30 human-graded pairs."

With n=30 the kappa has a wide confidence interval. State that honestly rather than over-claiming.

## Part 4: Metrics

Computed over top-10 retrieved results per query.

### recall@k (k = 1, 5, 10)

Fraction of queries where at least one result with grade >= 2 appears in the top k.

### MRR

For each query, find the rank of the first result with grade >= 2. Score 1/rank, or 0 if none. Average across queries.

### NDCG@10

```
DCG@10  = sum over i=1..10 of  (2^grade_i - 1) / log2(i + 1)
IDCG@10 = same, over the observed grades sorted descending
NDCG@10 = DCG / IDCG
```

IDCG uses grades observed for that query, not the whole corpus. This is the standard practical approximation - note it in the writeup.

### Breakdowns

Overall, plus by language (en / pl / de / es). The language breakdown is the most likely to surface something worth writing about, since it directly tests the boost mechanism.

Report n alongside each cell. With 5 Spanish queries, don't over-read that row.

## Part 5: Harness

### Files

- `src/eval/generate_vibe_queries.py` - LLM generation
- `src/eval/curate_queries.py` - keep/delete CLI
- `src/eval/judge.py` - LLM judge with caching
- `src/eval/grade_calibration.py` - human grading CLI
- `src/eval/calibrate.py` - agreement metrics
- `src/eval/metrics.py` - recall@k, MRR, NDCG, kappa
- `src/eval/run_vibe_eval.py` - main harness

### run_vibe_eval.py flow

1. Load `data/eval/vibe_queries.json`
2. Per query: run retrieval in `vibe` mode, top 10
3. Per result: grade via judge (cache-first)
4. Compute metrics
5. Write `data/eval/results_<timestamp>.json` with per-query detail
6. Print summary table

### Output shape

```
=== Vibe Search Eval - 2026-08-15 14:32 ===
Config: bge-base + bge-m3, language boost +0.1, no reranker, 8-line chunks
Judge: openai/gpt-oss-120b (weighted kappa = 0.78, n=30)

Overall (n=100)
  recall@1   0.62
  recall@5   0.88
  recall@10  0.94
  MRR        0.71
  NDCG@10    0.68

By language
  en (70)    MRR 0.74   NDCG 0.71
  pl (15)    MRR 0.61   NDCG 0.58
  de (10)    MRR 0.65   NDCG 0.62
  es (5)     MRR 0.58   NDCG 0.55
```

The config line must be recorded in the results file. Comparing runs across changes is guesswork without it.

## Success criteria

- 100 queries in `data/eval/vibe_queries.json`, distribution ~70/15/10/5
- 30 human-graded pairs in `data/eval/calibration.json`
- Weighted kappa >= 0.60 (iterate on prompt if not)
- Full eval runs end-to-end and writes a results file
- Judge cache works - second run makes near-zero LLM calls
- Baseline numbers recorded and committed

## Known risks

- **No ground-truth labels.** Everything rests on the judge. Calibration is the only check, hence non-negotiable.
- **Small calibration set.** n=30 gives a wide CI on kappa. Acceptable for portfolio work; state the limitation.
- **Judge self-consistency.** Same pair may get different grades across calls. Worth spot-checking 10 pairs twice.
- **LLM query bias.** Generated queries may cluster around whatever phrasings the model finds natural. Curation helps; the risk remains.
- **Groq rate limits.** 30 RPM means ~35 min for a full uncached run.
- **The judge and the retriever may share blind spots.** Both are transformer models trained on overlapping web text. If both misunderstand a query the same way, the eval scores it as a success. No cheap fix; worth naming in the writeup.
